## Findings

1. **major**: Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubClient.swift:158. A management 403 is reported as `.badKey` ("rejected the management key. Check the key in Settings"). CLIProxyAPI sends 403 when remote management is disabled (its default for remote clients, which a Tailscale hub is), when no key is set, and when the client IP is banned after 5 failed attempts. It sends 401 only for a missing or invalid key. Fix: map only 401 to `.badKey`. Give 403 its own case (for example `.accessDenied`, with copy like "The CLIProxyAPI hub refused management access. Make sure remote management is enabled on the hub, or wait if this Mac was blocked after failed attempts.") and categorize it, likely as `.authInvalid`. Then split `testBadKeyIsReportedAsBadKey` into a 401 test and a 403 test.
2. **major**: Tests/OpenUsageTests/CLIProxyHubClientTests.swift:290-304. The criterion says to use the fixtures from t3code's `cliproxyApi.test.ts` and the `usage-limits-hub` fixture. They are not in this repo, and the tests use hand-written payloads instead. I checked the hand-written shapes against CLIProxyAPI's source (auth_files.go, api_tools.go), and they agree on field names and types, so the risk is lower than the build report suggests. Still, the criterion is not met as written. Fix: the owner gives the path to t3code's fixtures and the auth-files and api-call payloads are ported verbatim, or the owner waives the provenance clause. Either way, make the `authFiles` fixture look like a real hub entry (`name`, `type`, `status`, `observed_at` next to `files`, and an `id_token` with only `chatgpt_account_id`/`plan_type`).
3. **major**: Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubClient.swift:67. In production, "bodies never appear in logs" depends only on the default `URLSessionHTTPClient(logsErrorBodies: false)`. No test covers it: the redaction test injects `RoutingHTTPClient`, so it would still pass if the default were `URLSessionHTTPClient()` and every hub error body were previewed into the log. Fix: add a test such as `XCTAssertEqual((CLIProxyHubClient(hubURL: url, managementKey: "k").http as? URLSessionHTTPClient)?.logsErrorBodies, false)`.
4. **minor**: Sources/OpenUsage/Providers/ErrorCategory.swift:248-257. Nothing tests the `CLIProxyHubError` → `ErrorCategory` mapping, which is the "categorized" half of the error criterion. Fix: add a small test that checks each case's category (`.badKey` → `.authInvalid`, `.httpStatus(502)` → `.http5xx`, `.timeout`/`.unreachable`/`.untrustedCertificate` → `.network`, `.invalidResponse` → `.decoding`, plus the new 403 case from finding 1).
5. **minor**: Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubClient.swift:41. `.httpStatus` always says "Try again later". The two hub statuses users will actually hit are not transient: `api-call` returns 400 when `$TOKEN$` can't be resolved (the account's token is missing or expired on the hub), and a wrong path prefix gives 404. Fix: for 4xx, word the copy so it points at the URL or the hub account, or leave a note that Issue 03's runtime maps the `api-call` 400 to the re-login error.
6. **minor**: Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubClient.swift:88-90. An entry without `provider` is skipped silently: it never reaches the `unusable` warning. CLIProxyAPI's disk-fallback listing (`listAuthFilesFromDisk`, used when the hub has no auth manager) emits `type`, not `provider`, so such a hub would show zero accounts with nothing logged, against AGENTS.md's "no silent fallbacks". Fix: fall back to `type` when `provider` is absent, or count skipped entries without a provider in the logged warning.
7. **nit**: Sources/OpenUsage/Services/HTTPClient.swift:25-29. The NOTE above `URLSessionHTTPClient` still says every HTTP error (>= 400) adds a body preview. That now depends on `logsErrorBodies`. Fix: mention the flag in that comment.
