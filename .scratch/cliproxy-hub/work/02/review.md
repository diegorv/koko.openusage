## Findings

1. **blocker** — Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubCards.swift:38. If two hub accounts map to the same card id, the app crashes at launch, and keeps crashing on every launch until the user edits the file. This happens with a duplicated hub block, a duplicated account entry, or ids that differ only in case (`ProviderAccountID.make` lowercases the identity key). `WidgetDataStore.init` builds `Dictionary(uniqueKeysWithValues:)` over provider ids (WidgetDataStore.swift:154). I reproduced it with a throwaway probe test: a hand-written config with accounts `a.json` and `A.json`, built into the catalog, registry and data store, fails with `Fatal error: Duplicate values for key: 'claude@c0b57498'` (signal 5). The probe was deleted afterwards. The config is a file boundary, and the new doc tells users to write it by hand. Fix: in `claudeRuntimes(hubs:)`, keep only the first runtime per card id (and per hub id), log the duplicate with `AppLog.error`, and add a regression test.
2. **minor** — Sources/OpenUsage/Stores/WidgetDataStore.swift:449. `hasMultipleClaudeCards` counts every `claude` card in the registry, hub cards included. When a hub card exists and the local default Claude card's identity is unresolved (`DefaultAccountObserver.Outcome.unresolved`), the local card's machine-local history is now left out of the synced history document ("omitting Claude history without account ownership"), though nothing changed locally. Hub cards have no history descriptor. Fix: count only the Claude cards in `registry.historyDescriptorsByProvider`, or leave out the `cliproxy` cards. Add a test.
3. **minor** — Sources/OpenUsage/Stores/FirstLaunchSetup.swift:103 (side effect of the wiring at AppContainer.swift:73). On the welcome screen, "Connect" for Claude now also turns on and refreshes every hub card. If the hub is down, that hub card is turned back off and the whole Claude row shows the hub error as failed, even when the local Claude card connected. On a fresh install, `FirstRunSeeder` also baselines the hub ids as known with nothing on, so `enableNewCards` never turns them on. That contradicts docs/providers/cliproxy-hub.md:37 ("A new hub card turns on the first time it appears"). Fix: skip `cliproxy` cards in `connect`, or document the fresh-install behavior. At minimum, correct the doc line.
4. **minor** — Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubCards.swift:27. An unreadable or malformed `cliproxy.json` is only logged. All hub cards disappear with nothing shown to the user. AGENTS.md "Error Handling" asks for a friendly user-facing error as well. This is acceptable to defer to Issue 07 (Settings), but say so in the Issue or ledger.
5. **minor** — The plan's Errors section (Q6) says hub-wide failures reach all cards "without each entering its own cooldown". Each hub card still gets WidgetDataStore's own 60 s `failureRetryAfter` (WidgetDataStore.swift:348/371). The cards fail in the same pass, so they back off together and the visible effect is small. Still, this departs from the plan, and the build report only notes it. Confirm with the owner or record the decision.
6. **minor** — Missing tests: nothing exercises hub cards through `UsageReader` (CLI) or `LocalUsageAPI`. UsageReader.swift:58 hard-codes the default `CLIProxyHubConfigStore()`, so the CLI path can't be tested with an in-memory config. Consider passing the store in, then add a CLI or HTTP API test that shows a hub card's limits.
7. **nit** — Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubSession.swift:61. `CLIProxyHubSession.Transport` duplicates Issue 01's `CLIProxyHubHTTPClient`, which production code no longer uses (only CLIProxyHubClientTests do). Pick one adapter.
8. **nit** — Tests/OpenUsageTests/CLIProxyClaudeRuntimeTests.swift:190. `XCTAssertEqual(peak, 4)` depends on 10 tasks overlapping within a 30 ms sleep. On a loaded CI runner the peak could fall below 4. `XCTAssertLessThanOrEqual(peak, 4)` plus a check that the peak is above 1 would hold up better.

## Resolution

1. **Fixed** in `b950d742`. `CLIProxyHubCards.claudeRuntimes` keeps the first hub per hub id (case-insensitive) and the first card per card id, and logs each skipped duplicate with `AppLog.error(.config, …)`. Regression test `testDuplicateHubsAndAccountsKeepTheFirstCardAndStillBuildTheDataStore` (repeated hub, `a.json`/`A.json`/`a.json`, and a hub id that differs only in case) builds the catalog, registry and `WidgetDataStore`. Before the fix it crashed with signal 5, the same way as the probe.
2. **Fixed** in `eb23bd07`. `hasMultipleClaudeCards` now counts only Claude ids in `registry.historyDescriptorsByProvider`. Test `testHubCardsDoNotDropTheLocalClaudeHistoryFromSync` failed before the fix and passes after.
3. **Fixed** in `a598315f`. `FirstLaunchSetup.connect` skips `CLIProxyClaudeRuntime` cards, so a down hub no longer fails the Claude row or turns anything on. Test `testConnectLeavesHubCardsAlone` failed before the fix (the row showed the hub error) and passes after. On a fresh install hub cards still start off. That matches "fresh installs start with nothing on", so I corrected the docs instead of changing it: docs/providers/cliproxy-hub.md ("Cards") and docs/provider-enablement.md now say that hub cards start off on a fresh install and get turned on in Customize.
4. **Deferred to Issue 07** (no code change). A malformed `cliproxy.json` is still only logged (`CLIProxyHubCards.swift:27`). The only user-facing place for that error is the hub Settings UI that Issue 07 builds. Issue 07's criteria don't mention it yet, so the main session should add it to the ledger or to Issue 07 (this step must not edit the ledger).
5. **Kept as is; needs owner confirmation.** Each hub card still gets `WidgetDataStore`'s own 60 s `failureRetryAfter` (WidgetDataStore.swift:348/371). Every card of a down hub fails in the same pass (refreshAll runs them together, and `CLIProxyHubSession` shares the one hub error), so the cards back off together and retry together. The visible behavior is the one Q6 asks for: one hub error and one retry time across the cards. Dropping the backoff for hub cards would let a wake burst probe a down hub again on every wake. Treat this as the recorded decision unless the owner wants hub cards to skip the per-card backoff.
6. **Partly fixed** in `91ff2325`. `testHubCardLimitsAreServedUnderTheClaudeFamily` (UsageReaderTests) feeds hub card runtimes through `UsageReader.read(providerID: "claude")`, which builds its response with `LocalUsageAPI.respond`. It checks that the hub card's `session` and `weekly` limits come back under its card id. **Rejected:** passing the config store into `UsageReader`. The non-override path also runs `ProviderAccountAssembly.make` and the real Claude/Codex homes, so an injected store still wouldn't make that path testable in isolation. The new test covers what the store would have enabled: hub cards through the CLI and API projection.
7. **Fixed** in `3b5c280e`. There is now one adapter: `CLIProxyHubHTTPClient` holds the hub's `CLIProxyHubSession`, and `CLIProxyHubSession.Transport` is removed. The session's init is `nonisolated` so Issue 01's `CLIProxyHubClientTests` can build it, and they now go through the session.
8. **Fixed** in `1f0f3300`. The test now asserts `peak <= CLIProxyHubSession.maxConcurrentCalls` and `peak > 1`.
9. Not addressable here. The owner's config has 0 cached accounts, so the smoke test waits on Issue 03 or a hand-written cache.
