## Findings

1. minor — Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubRelaunchNotice.swift:33-36 — If spawning the relaunch helper fails, the error is only logged and the click silently does nothing, while AGENTS.md "Error Handling" asks to also show a friendly error to the user. Practically unreachable (`/bin/sh` spawn), so not a blocker. Fix: either keep the card up and swap its message to a short "Couldn't relaunch, quit and reopen OpenUsage" text, or have the owner confirm the log-only default the build took.
2. minor — Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubAccountSync.swift:46-48 — Running hub cards capture `account.authIndex` at launch (CLIProxyClaudeRuntime.swift:28, CLIProxyCodexRuntime.swift:23). If the hub reassigns `auth_index` for the same account id, the cache is rewritten but no notice shows, and this launch's cards keep calling with the stale index until a manual relaunch. This is outside the Issue's literal "set of accounts" wording, so it is not a criterion failure. Fix: confirm with the owner whether `auth_index` is stable across hub restarts; if not, also treat an `authIndex` change on an existing id as a change.
3. nit — Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubRelaunchNotice.swift:1 — An `@Observable` UI notice store that imports AppKit and terminates the app lives in the provider module, while comparable stores (`OnboardingStore`) live in `Sources/OpenUsage/Stores/`. Fix (optional): move it to `Stores/`.
4. nit — Sources/OpenUsage/App/AppContainer.swift:81-83 — The wiring from `run() == true` to `markChanged()` and the `relaunch()` process path have no automated test; the relaunch is hard to unit-test, and the build report says it was not tried in the running app. Fix: a manual check before release (edit the cached `accounts` in `~/.config/openusage/cliproxy.json`, launch, click Relaunch).
