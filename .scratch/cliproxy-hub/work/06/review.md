## Findings

1. minor — Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubLocalMatch.swift:73-75 (test at Tests/OpenUsageTests/CLIProxyHubLocalMatchTests.swift:45). When both sides have a Codex account id, matching uses the id alone. This codebase treats a Codex identity as `accountID|email` (`CodexAccountIdentity.key`, CodexSwapAccount.swift:9), so two different users in the same ChatGPT Team workspace count as different accounts. Here, a local login for user Y is hidden when the hub holds user X in the same workspace, and Y's limits and spend then show nowhere. This follows the Issue's literal wording ("match by ChatGPT account id"), so it is not a blocker. Fix: ask the owner to confirm. If seats should count as separate accounts, require the emails to match too when both sides have one, and turn the "same id, different email" test case into a no-match case.
2. minor — Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubLocalMatch.swift:25-30. A Claude email hides every local card with that email, across all of its organizations. The hub holds an OAuth login for one organization, so a local card for a different org (a separate usage pool) is hidden without a hub card to replace it. This is the literal rule, and discovery.md lists it as a risk. Fix: get explicit owner confirmation, or note in docs/provider-enablement.md that all organizations of the email are hidden.
3. minor — docs/provider-enablement.md:33 and CLIProxyHubLocalMatch.swift:59-67. The hidden set is built from every hub card in the config, whatever its Customize toggle says. A user who turns the hub card off in Customize, expecting the local card back, gets neither card. The docs say "disable the hub", which a reader can take to mean that toggle. Fix: name the control in the docs (the hub's `enabled` flag in `cliproxy.json`, or removing the hub). Alternatively, if the owner prefers, leave out of the match any hub card that is turned off.
4. minor — Tests/OpenUsageTests/CLIProxyHubLocalMatchTests.swift:85. No test covers the account-card path of `localAccounts`: the Swap-slot email, and an org card's email from the account-UUID join in `ProviderAccountAssembly.claudeEmailsByUser`. That join is new logic, and the build report admits the gap. My throwaway probe passed, but a regression there would go unnoticed. Fix: add a test that builds an assembly with Swap and org cards, or runs `make(observer:)` with a Swap fixture as in ProviderAccountAssemblyTests, and asserts each card's email.
5. nit — docs/provider-enablement.md:32. "the hidden card's on/off setting is kept" is true for enablement. Layout is a different story: `LayoutBootstrap` drops descriptors that are not in the registry, and the next layout edit saves the list without them. So pins and metric choices made for the hidden card can be lost while it is hidden. When the card comes back, its default metrics are seeded again. Any card that disappears already behaves this way. Fix: none required. Optionally mention it as a heads-up in the PR.
6. nit — Sources/OpenUsage/App/AppContainer.swift:91, Sources/OpenUsage/Services/UsageReader.swift:66. The same one-line wiring is duplicated, and no test checks that either launch path passes the hidden set. Fix: optional. A shared helper or a UsageReader-level test would catch a dropped argument.
