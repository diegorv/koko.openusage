## Findings

1. blocker — .scratch/cliproxy-hub/work/07/ — The screenshot criterion is not met, and AGENTS.md requires screenshots for a visual PR. Fix: render the section with the Add Hub form open (light and dark, card alone, like Issue 05's PNGs) and commit them under work/07/; then check the rendering against the design language claim in criterion 5.
2. minor — Sources/OpenUsage/Views/CLIProxyHubSettingsSection.swift:111 (and CLIProxyHubSettings.swift:32) — `actionError` is never cleared by Cancel, `openForm()` or `reload()`. Scenario: type `hub.example`, press Save (error "Enter the hub's full URL…"), press Cancel: the error stays under "Add Hub", and it is still there after leaving and reopening Settings, until the next successful save. Fix: clear `actionError` when the form closes or opens and in `reload()`, with a test.
3. minor — Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubSettings.swift:112-113 — Every save starts a new, unserialized `CLIProxyHubAccountSync.run()`. Toggling a switch a few times runs several full syncs at once (each lists accounts on every enabled hub), alongside the launch sync in AppContainer. This breaks the "Hubs are synced one after another so the config's load/modify/save never races itself" invariant (CLIProxyHubAccountSync.swift:6). `saveAccounts` runs its load and write on a detached task, so a Settings save on the main actor that lands in between gets overwritten: a newly added hub or key can vanish from the file while the Settings list still shows it. The window is small, and the build report discloses it. Fix: keep one in-flight sync (skip or chain a new request while one runs), or ask the owner whether the race is acceptable.
4. minor — docs/provider-enablement.md:33 — It still tells users to remove the hub "from `cliproxy.json`" or set `enabled` to `false` there to bring a local card back. Removing or disabling is now a Settings action (AGENTS.md: logic changes update the docs that describe them). Fix: mention Settings → CLIProxyAPI Hubs.
5. minor — Tests/OpenUsageTests/CLIProxyHubSettingsTests.swift:74 — The chosen default "re-adding a saved URL keeps its on/off state" has no test: `testAddingASavedURLKeepsItsIDAndAccounts` uses an enabled hub and never asserts `enabled`. The failed-save path (`actionError` set, no notice, no sync) is untested too. Fix: seed a disabled hub and assert it stays disabled after re-adding; add a failing-write `FakeFiles` case.
6. nit — Sources/OpenUsage/Providers/CLIProxyHub/CLIProxyHubSettings.swift:112 — The dashboard's "Hub Accounts Changed — Relaunch OpenUsage to show the hub's current accounts." card now also appears for a Settings disable or remove, where the copy is slightly off. It is acceptable for "offers the relaunch prompt". Fix (optional): none required; note it for the owner.

## Resolution

1. Fixed in f5243328. `add-hub-form-light.png` and `add-hub-form-dark.png` under work/07/ show the card alone with two hubs (one on, one off) and the Add Hub form open and filled in. They were rendered off-screen with a throwaway NSHostingView harness on a fake config, which was then removed (nothing in the committed diff). The owner's running app was not touched. Because the off-screen window is never key, the "on" switch and the Save button use the inactive-window tint (grey, not accent blue).
2. Fixed in 76be283b. `reload()` clears `actionError`, and a new `clearActionError()` runs when the form opens and when it closes (CLIProxyHubSettingsSection.swift `openForm`/`closeForm`). Test: `testTheErrorClearsWhenDismissedOrReloaded`, which failed before the fix.
3. Fixed in dc8a2642, on both sides:
   - The lost write: `CLIProxyHubConfigStore.exclusively` holds a process-wide lock. `saveAccounts` and the Settings `update` each run their whole load/modify/save inside it, so neither can overwrite the other. Test: `CLIProxyHubConfigStoreTests.testSavingAccountsWaitsForAnExclusiveChange`, which lost the write before the lock (red) and passes after.
   - Concurrent syncs: `CLIProxyHubSettings.requestSync()` keeps one Settings sync in flight. A save made while it runs queues a single follow-up pass, so the newest hubs still sync. Test: `testSavesDuringASyncQueueOneMorePassInsteadOfAnotherSync` (3 calls before the fix, 1 then 2 after).
   - The launch sync and a Settings sync can still overlap. That only costs a duplicate network round, since the lock makes their writes safe.
4. Fixed in f0b5a61b. docs/provider-enablement.md:33 now points to "Settings → CLIProxyAPI Hubs" (turn the hub off or remove it).
5. Fixed in 6a2a0312. Two new tests: `testAddingASavedURLKeepsItsOnOffState` (a disabled hub stays disabled after it is re-added) and `testAFailedSaveIsAFriendlyErrorWithoutRelaunchOrSync` (an unwritable store sets `actionError`, adds no hub, shows no notice, and starts no sync).
6. No code change, as the review allows. Note for the owner: disabling or removing a hub in Settings also raises the dashboard's "Hub Accounts Changed" card, whose copy is written for account changes.
