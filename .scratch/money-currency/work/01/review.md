## Findings

1. minor — docs/local-http-api.md:146 — The comment says the format carries `"currency"` only "when not USD", but the mapper stores a payload "USD" as `"USD"` (ClaudeUsageMapper.swift:221), so a Claude USD account emits `"currency":"USD"` in `/v1/usage`. Fix: reword to "(+ \"currency\" when the provider reports one; absent means USD)", or normalize "USD" to nil in the mapper.
2. nit — Sources/OpenUsage/Providers/Claude/ClaudeUsageMapper.swift:244-245 — The diff adds a second blank line before `resetDate`. Fix: remove the extra blank line.
3. nit — Sources/OpenUsage/Services/LocalLimitsAPI.swift:137-139 — The edited doc comment now runs to about 170 columns on line 138 while the lines around it wrap near 100. Fix: rewrap the comment.
4. nit — Sources/OpenUsage/Providers/Claude/ClaudeUsageMapper.swift:223 — A `decimal_places` outside 0...4 (or non-integer) quietly falls back to 2 (or is rounded) with no log, which sits uneasily with AGENTS.md's "fail loudly" rule. Fix: log the unexpected value when falling back, or accept as-is since it matches the old cents behavior.
5. nit — Sources/OpenUsage/Support/MetricFormatter.swift:48 — Row/full money always uses two fraction digits, so a zero-decimal currency prints "¥500.00". Out of scope for BRL/USD; consider deriving digits from the currency (or `decimal_places`) in a follow-up.

## Resolution

1. Fixed: docs/local-http-api.md now says the format carries `"currency"` when the provider reports one, and that absent means USD.
2. Fixed: removed the extra blank line before `resetDate` in ClaudeUsageMapper.swift.
3. Fixed: rewrapped the `progressUnit` doc comment in LocalLimitsAPI.swift near 100 columns.
4. Rejected: an out-of-range or non-integer `decimal_places` falling back to 2 matches the old cents behavior, and the field is optional; adding a log path for a value Claude has not been seen to send is speculative code.
5. Rejected for this Issue: zero-decimal currencies (JPY) are out of scope for the BRL/USD acceptance criteria; left as a follow-up.
